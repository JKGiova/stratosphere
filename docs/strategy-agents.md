# Orchestrator and strategy agents

Status: implemented foundation, October 18, 2026. The broader [Phase 3–5 acceptance ledger](phase3-5.md) remains in progress.

The orchestrator bridges the user to one stable agent identity per exact strategy definition. Each specialist has its own private local history, source/evidence context, attached jobs and retained reports. It analyzes its own rules; the orchestrator selects the destination and hands back results. The specialist chat uses LangGraph. Shared model transport does not mean shared strategy conversation state.

Create a reviewed strategy with `/new`. Once its behavior is complete, registration atomically creates/reuses its 24-digit public ID and its agent. Exact duplicates preserve the agent and accumulate submissions/sources; behavior changes receive a distinct identity. `/agent` lists identities; `/agent <full-strategy-id>` or selecting a Library row chooses its specialist. A general conversation with no registered strategy stays in the orchestrator. Natural-language routing among registered strategies validates the model's action and target; switching targets requires an explicit ID or unambiguous matching name in the user's request.

A specialist can analyze retrieved evidence, show measured reports or request its existing test plan. It can also propose an editable [bounded SMA study](phase3-studies.md), including the baseline and distinct nearby pairs. The application computes the finite minimum budget; model hypotheses are unverified proposals for human review. Unapproved tests show the exact plan for review; an already approved paused plan can resume through the same operation as `/resume`. The model cannot approve a plan, issue SQL, import source code, expand permissions or start live trading. `/new`, `/study`, `/approve`, `/pause`, `/resume`, `/show`, `/report` and cancellation retain their deterministic checks. The [dated applicability workflow](phase3-applicability.md) adds exact-identity evidence and local candidates; broader strategy families, authenticated community recommendations, actual current-market providers and paper operations remain subsequent work.

Library now shows stable strategy IDs and their agents. Tests shows actual research jobs. **Reports replaces Session**, listing completed research and source-review reports and displaying their deterministic metrics, limitations and immutable references. Selecting a report verifies its original research artifact seal and online availability again. The panel supports all existing six/four/two/one responsive layouts. Model/request details remain in the status bar and its tooltip. No synthetic performance, account or position is shown.

Keys remain in memory. General chat is session-only; completed strategy-agent turns are retained privately in `workspace.sqlite3` under the research directory. Failed/canceled partial turns are excluded. `/clear` removes the selected agent's local conversation, or the general conversation when no strategy is selected; immutable research evidence remains. Onboarding discloses the local history retention. Native workers receive no model/service credentials.

The local SQLite registry is a private development harness, not a deployed shared-user service or a replacement for Supabase. Supabase now has the selected project's private schema and tested ownership policies; hosted service/authenticated synchronization is not yet wired into the TUI. No database service key is copied to clients. See [database development](../supabase/README.md).

Ollama routing uses its native JSON-schema response format and requests `reasoning_effort=none`. Workflow output remains strictly validated; malformed JSON, duplicate fields, invented IDs/actions and changed source text cause an explicit failure without execution. Other adapters retain prompt-based JSON with the same deterministic validation. This does not claim equal model reliability or tool support across providers.

## Verification

The local foundation passed identity/source/deduplication/concurrency, per-strategy isolation, cancellation/failure, cross-strategy routing, report integrity and restart tests. A real local Ollama run used the already installed Spark-X2.5 1.7B model, routed two requests to two distinct strategy agents, produced their analyses, checked that the other strategy's context was absent and restored the first agent's completed history after restart. The two routing-plus-analysis turns completed in 11.684 and 12.509 seconds, with four model calls total. An earlier unconstrained routing attempt exhausted its token budget; schema-constrained output and disabled reasoning were verified subsequently. These checks do not establish profitable strategies or broad model equivalence.

The live Supabase SQL harness passed canonical hashes against the repository's authored specification, duplicate reuse, variant lineage, one stable agent identity, separate private sessions per owner, immutable reports and ownership isolation. All fixtures and temporary grants rolled back; final queries showed zero retained strategies/profiles, 13 RLS-enabled tables and no anonymous/direct-client schema access. Security advisors returned no findings. The report ownership FK index was added following the performance advisor; fresh unused-index informational notices remain expected on an empty database, not a reason to remove required relationship indexes. [Advisor explanation](https://supabase.com/docs/guides/database/database-linter?lint=0005_unused_index).

The foundation's final local suite passed **403 tests with zero skips**, including seven tests against the pinned native engine. The 29 existing upstream Pandas deprecation warnings remain visible. Ruff lint/formatting, natural-language approval/resume/report/form integration checks, and the isolated built-wheel onboarding/Reports checks passed. No new hosted-provider live access or Phase 3–5 completion is claimed. Publication uses `[skip ci]` so these checkpoint commits do not start GitHub runners; no workflow or billing setting was changed. ## Source-review operations

A specialist can now review an acquired snapshot through chat or `/source-review <source-id> [strategy-id]`. Exact quotes and immutable snapshot references are validated by the application; completed private reports appear in Reports. Only the owning agent’s latest verified reviews enter later analysis context. Failed/canceled requests retain attempts without partial conversation turns. This compares material against an existing registered strategy and does not register, convert, approve or test extracted rules. See [source-review evidence and limits](source-reviews.md).

Source reviews now use numbered application-owned passages. Agents select evidence references; application code constructs and verifies exact quotes. An accepted citation does not verify the interpretation. Historical reports retain their original spans and hashes; see [passage protocol and verification](source-reviews.md).

[Registry-anchored studies](phase3-registry-studies.md) now let a registered definition or derived variant propose and run approved studies without a separate `/new` parent. The application owns the baseline and explicit requested pairs; model hypotheses remain unverified. In-flight operations retain the strategy selected at request start even when Library selection changes, and cannot acquire another strategy’s private history through that navigation race.
