The user selected Alpaca first for Bitcoin spot and Liquid later for perpetuals. This supersedes Liquid as the first real-feed paper route, not the full [Phase 3–5 requirements](phase3-5.md).

## Setup and fixed reads

Create a free Paper Only account through the [Alpaca dashboard](https://app.alpaca.markets/account/login) and generate the account's paper API key ID and secret. Dismiss model setup with Escape if needed, then run `/alpaca-connect`. Enter both values in the masked inline chat form and select **Check paper account**. No model is required. `APCA_API_KEY_ID` and `APCA_API_SECRET_KEY` can prefill the form from the process environment; a repository `.env` is not automatically loaded. Never paste credentials into ordinary chat.

Submission performs exactly three GETs against the fixed `https://paper-api.alpaca.markets` host: `/v2/account`, `/v2/assets?asset_class=crypto`, and `/v2/account` again. These [paper credentials and host are separate from live trading](https://docs.alpaca.markets/us/v1.1/docs/authentication-1). A base URL, alternative host, arbitrary route, HTTP method, model tool or live-mode switch is not configurable. Redirects, environmental proxies, retries and automatic fallbacks are disabled. Alpaca keys can carry broader provider permissions; this client uses only the two reviewed read shapes and supplies no order operation.

The second account read must match the first projected identity, currency, status and blocking fields. Credentials are frozen across awaits; disconnect/replacement/cancellation prevents late publication and further requests. Failures use fixed safe messages without provider bodies or headers. Overlapping checks are rejected. Inputs are cleared before the form closes. Active keys and redaction guards remain only in process memory; disconnect removes active access and the cached check, while redaction guards remain until process exit. Quitting cancels the worker and disconnects access. No keys enter model prompts, strategy histories, native worker environments or exports.

`/alpaca` explicitly refreshes the check. Focus shows its capture time, provider-reported account, exact BTC/USD asset metadata and limited observed blockers. `ACTIVE`, `tradable` and `fractionable` are reported fields, not approval, proof of legal account control or data/execution readiness. Missing crypto status remains unknown; an absent BTC/USD asset does not silently select BTC/USDT or another asset. Unknown/unrelated account fields are omitted. Native increment strings retain exact decimal values, including precision beyond the authored ledger's eight decimals. Response/request IDs and raw byte digests identify the reads, but omitted response bytes cannot be reconstructed or independently authenticated from a digest alone.

`/alpaca-save` explicitly saves the last completed check under `<research-state>/alpaca-checks/<id>/check.json` with a private manifest, after the application's online gate. Files are 0600 and directories 0700 on Linux/macOS; symlinks, known credential echoes, changed existing exports and damaged manifests are rejected. Re-exporting the same capture verifies its existing bytes. The reader reopens a historical check without restoring keys, connecting an account or granting authority. There is no automatic account-response persistence or sync to shared services. Raw response bodies are not exported. `/alpaca-disconnect` forgets active access without canceling orders or changing any broker state.

## Market, fees and remaining integration

[Alpaca documents crypto spot simulation](https://docs.alpaca.markets/us/docs/paper-trading) and [BTC/USD crypto asset metadata](https://docs.alpaca.markets/us/docs/crypto-trading). Actual account/asset availability, jurisdiction restrictions and data permissions still require verification for this account. No paper key has been exercised during development yet. Free paper access is not a blanket commercial data or redistribution license.

BTC/USD at Alpaca is distinct from the prior Binance BTC/USDT source, exact strategy identity, dataset and measured results. A future plan must pin the actual venue, quote currency, interval, native quantity/price increments and timing; existing spot results must not be relabeled. No price read, dataset acquisition, strategy registration or native test starts merely by checking account metadata.

The crypto documentation describes fees in the credited asset: a buy can charge base currency, while a sell can charge quote currency; activity reporting can be delayed. The existing authored ledger only models its declared quote-fee profile. It cannot be treated as a conforming Alpaca adapter by rounding away base fees or forcing provider precision into eight decimals. Funding/margin rules for Liquid perpetuals remain a different future profile. Execution stays unavailable until native fill/fee accounting, entitlement, deterministic mandates/risk, idempotency, partial fills, cancel/ambiguous handling, reconciliation, restart, sustained operation and the keep/request-all-closures exit workflow are implemented and verified.
