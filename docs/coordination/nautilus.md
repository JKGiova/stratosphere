## Interface

### Implemented and verified against source

`development/compiler.py:compile_strategy` emits `GeneratedStrategy(SignalProgram)`, not a native
Nautilus `Strategy`. `load_generated` accepts only exact application-generated bytes for a validated
specification. `development/worker.py:simulate` checks frozen implementation/code/snapshot pins before
calling `yahoo/engine.py:run_price_simulation`. That function wraps the program in a local native
`SmaStrategy(Strategy)` and runs `BacktestEngine`. The signal/native-host seam already exists, but
this host is a historical simulator, not a continuous MT5 runtime.

Supported behavior in `development/contracts.py:validate_program` and
`development/signals.py:SignalProgram.push`: one H1/D1 closed-bar stream, fixed quantity, one long
position, market entry/full exit, exit before entry, no reinforcement/shorting. Rational arithmetic,
warmup and prior signal state are application-owned. The simulator produces synthetic
next-available-open quotes, ample synthetic liquidity, cash-account fills and declared costs.
Submission expects exactly one synchronous full fill; `on_order_filled` sets a Boolean held flag.
Rejection aborts the run. This timing/Boolean is unsuitable for asynchronous or partial live fills.
Final exposure is marked, not automatically liquidated. See [strategy development](../strategy-development.md)
and [`run_price_simulation`](../../src/stratosphere/yahoo/engine.py).

`MT5Bridge` and `MT5Trading` provide guarded local operations, exact session/deployment binding,
consumed requests and durable uncertainty, not native Nautilus clients. The EA serves bounded
snapshots on a one-second timer, without an established continuous tick/event contract. Existing
operator/overnight execution is separate from this integration. Connection never enables trading.
See [MT5 bridge](../mt5-bridge.md) and [invariants](../invariants.md).

### Proposed shared runtime seam — no new accepted contract

Preserve the validated definition plus exact compiler/runtime bytes as the strategy decision source.
A native host should supply ordered finalized bars and confirmed strategy-owned exposure to the
same decision semantics. Keep signal identity/consumption, pending intent and actual filled quantity
separate. Native classes may wrap the existing program or evolve under a versioned compiler contract;
behavioral equivalence is the requirement, not identical inheritance.

Required strategy-owner inputs: exact definition/variant identity, capability declaration,
compiler/runtime hashes, data/time/volume semantics, warmup/startup policy, confirmed and pending
exposure semantics, sizing/stops/exit rules, evidence ownership and instruction/description references.
External packages remain owner-managed. The requested `developing-strategies/` and
`developed-strategies/` folders, each containing strategy subfolders with code, description and
instructions, are the owner's requested packaging requirement; the owning-module contract and
implementation remain pending review. This report creates no folders, loader, manifest/schema or
promotion lifecycle. Folder membership and instructions cannot authorize arbitrary Python or trading;
execution must retain the application compiler gate.

The native host should consume a capability-limited MT5 adapter. Every entry must traverse existing
exact deployment, finite budget, exposure, native SL, risk/margin/spread/freshness and durable request
gates. Unsupported native operations must return explicit unsupported outcomes. Owned protective
exits stay independent of models and entry expiry/revocation. Nautilus risk checks supplement these
application gates; they do not replace them or grant authority.

### Proposed deep module and first interface

The Nautilus module should hide native configuration, validated loading, causal event delivery,
host-owned pending/exposure state and native result normalization behind an application-facing
interface. Callers should not assemble native strategies, caches or clients. It consumes existing
strategy contracts rather than introducing another strategy representation. These are design
proposals, not callable operations or accepted peer contracts.

| Responsibility | Owning module / proposed placement |
| --- | --- |
| Definition, generated bytes, package contents and promotion between the requested folders | Strategy contracts and compiler; Nautilus consumes verified identity and supported behavior, never scans folders to activate strategies. |
| Frozen research campaign, target/cost ownership, finite start reservations and comparative report sealing | Existing development orchestration; keep this above individual native runs. No second campaign scheduler inside Nautilus. |
| Recheck frozen cell/code/data, construct the native host, drive one bounded run, normalize its evidence | Nautilus module; credential-free historical worker remains its process isolation mechanism. |
| Native data/execution client factories, broker conversion and transport | MT5 Python connector, consuming the pinned native extension interfaces; EA retains terminal-side checks and confirmations. |
| Deployment approval, account lease, durable request consumption and uncertain broker outcomes | Existing MT5 authority/journal path; native host retains only reconciled projections, never a competing source of broker truth. |
| User/tool presentation | CLI/MCP call the same application operations, without importing native classes or reproducing validation. |

First implementation target: one offline operation, conceptually
`replay(frozen_cell_ref, reserved_start_ref, cost_case) -> ReplayReceipt`. Names and receipt schema
are provisional. Resolve references from application-owned storage; a caller-supplied hash or
reservation string alone establishes neither authority nor a remaining start. The owning campaign
must reserve the exact native start before dispatch. The worker rechecks its complete frozen inputs,
and completion/failure is recorded against that same reservation without allocating another one.
Current base/stress cases remain separate consumed starts within the existing frozen budget.

The request binds the existing `CellPlan`, exact generated code and `PriceSnapshot`, concrete
strategy/market owner, cost case and bounded attempt. Return normalized signals/fills/equity and
immutable evidence references with the exact input, code, implementation and engine pins. Failure,
cancellation and interruption retain an incomplete/failed attempt; they do not fabricate a successful
empty result. Re-delivery may inspect a retained outcome but must never execute a consumed or
uncertain start again. Receipt compatibility with existing reports/readers must be verified before
introducing a new schema. `replay` here means historical evaluation, never permission to retry.

Keep live operations distinct from this first interface: future read-only observation needs a bounded
lifecycle and freshness/status evidence; future deployment needs an exact approved deployment and
reconciled broker state. Neither a generic `mode=live` flag nor folder membership upgrades a replay
request into execution authority. Stopping entries must preserve independently owned protective
exits; process shutdown cannot silently abandon exposure. These live contracts remain blocked by
the data/execution proposals below, so do not publish invented operation signatures yet.

Use the existing `signals_factory`/`push(bar, held)` seam internally for supported historical
semantics. It already has two concrete callers: generated programs through `worker.simulate` and
legacy SMA through `yahoo.engine.run_simulation`. Preserve both historical readers and result
contracts. Do not expose indicator windows or native callbacks to callers, and do not extend the
Boolean exposure interface to live partial fills without a separately versioned strategy contract.
Do not introduce a generic broker framework: the only active broker is MT5, and its future native
clients must satisfy the existing pinned extension interfaces.

### Design tradeoff and test surface

A shared native superclass would couple the compiler to native lifecycle details without solving
authority or recovery. A thin facade over `run_price_simulation` would leave input checks and evidence
handling scattered in callers. Prefer a deep offline module that owns those responsibilities while
retaining the signal seam and credential-free process isolation. Deleting that module would force
each caller to reconstruct the validation, causal execution and evidence behavior; that is the
intended leverage. Native host class structure remains an internal implementation choice.

Signal evaluation is in-process pure computation; frozen artifacts are local filesystem dependencies;
Nautilus is a pinned third-party dependency exercised by native integration fixtures. Inject the
existing worker runner for orchestration failure/cancellation tests, but use the actual pinned engine
to establish native signal/fill parity. A mock engine cannot establish that parity. Test observable
receipts and retained failed attempts through the application interface, not private native callbacks.
Retain historical compatibility tests; remove duplicate implementation-coupled tests only after
equivalent behavioral coverage exists, not as part of this documentation task.

## Dependencies and blockers

Strategy revision 1 has no agreed runtime/package contract. Connector and EA revision 1 have no
accepted native-client/report extensions. CLI/MCP revision 1 must consume shared operations once
agreed; peer report proposals are not implemented interfaces.

Deterministic decisions can match when finalized bars, warmup, definition and confirmed exposure
match. Real fills, latency, partials, rejection, financing and broker stops alter subsequent exposure;
identical returns or future signals cannot be promised from this full-fill cash simulator. Source
conformance, MT5 historical UTC/session semantics, CFD costs and sustained feed/restart behavior remain
unresolved. Mandatory SL blocks unchanged deployment of the current no-stop research behavior.
Portfolio allocation/FTMO reset rules are not solved by a native client.

## Proposals for owner review

1. **Strategy + Nautilus:** agree decision inputs/output and versioned identity, package validation
   and persistence requirements. Preserve external ownership and compiler-only execution. Leave
   folders/schema/lifecycle implementation to the owning module. Review the first offline interface

2. **Nautilus + connector + EA:** agree the capability matrix, instrument/OMS mapping, polling and

   protocol/approval-pin changes require separate reviewed implementation.
3. **Staged acceptance:** first offline deterministic replay under pinned 1.231.0 for current
   semantics, comparing warmup/indicator state, exit precedence, signals, synthetic fills and evidence
   with existing backtests, including duplicate/gap/tamper cases. Then read-only MT5 streaming with
   trading disabled: verify closure/time mapping, warmup, freshness, duplicate/revision handling and
   disconnect/account-switch/restart halts. Only after those gates and a validated full CFD variant,
   separately authorize exact demo execution covering confirmed/partial/rejected/uncertain outcomes,
   restart/no replay and owned exits. Offline replay does not establish live partial-fill parity;
   demo acceptance grants no real-account activation.
